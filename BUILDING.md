# Building Welt

## UI dependencies

Welt uses [Modern Docking](https://github.com/andrewauclair/ModernDocking) 1.4.9 for its Swing tool panels. Maven resolves it from Maven Central; commercial JIDE docking JARs, evaluation downloads and licence keys are not required. The remaining checkbox-tree, tri-state and rotated-label widgets use the open source `jide-oss` 3.7.15 artifact from Maven Central.

Modern Docking layout data is stored separately from legacy JIDE layout data. Existing JIDE layouts remain in the configuration for recovery; they are not interpreted as Modern Docking XML. The first run uses the default arrangement until a Modern Docking arrangement is saved.

## Set up Maven toolchain
WorldPainter uses the [Maven toolchain framework](https://maven.apache.org/guides/mini/guide-using-toolchains.html) to find the JDK it needs. You need to follow the instructions on that page to configure a toolchain of type jdk and version 17 pointing to a Java 17 JDK. Note that it has not been tested whether WorldPainter will run correctly on older Java versions if you substitute a newer JDK for version 17, although in theory that should work.

## Build WorldPainter
Once all dependencies are installed and the toolchains set up you can build WorldPainter from the command line or using your favourite IDE by invoking the `install` goal on the `WorldPainter` module. There are some rudimentary tests, but they take a while to run and don't contribute much, so I recommend skipping them by adding `-DskipTests=true`.

## Run WorldPainter
Once it is built, you can run WorldPainter by invoking the `exec:exec` goal on the `WPGUI` module, or by running the main class: `org.pepsoft.worldpainter.Main`.

## Develop WorldPainter
For a few pointers, pitfalls and gotchas about developing WorldPainter, see [this page](https://www.worldpainter.net/trac/wiki/DevelopingWorldPainter).

## More details
For a more detailed description of the build process, see: https://www.worldpainter.net/doc/building.

## Building Welt with native acceleration
Welt adds an optional native (Rust) acceleration layer. To build with it, use the Maven profile `-Pnative`: it invokes `cargo build --release` (via exec-maven-plugin) and copies the resulting native library (e.g. `welt_core.dll`) into `WPCore/src/main/resources/natives/<os>-<arch>/`, after which the build proceeds normally.

Without `-Pnative`, nothing changes: the build remains 100% Java and WorldPainter behaves exactly as before (native acceleration is opt-in at runtime via the `wp.native.gen`, `wp.native.render` and `wp.native.export` system properties, which default to `false` and fall back silently to the Java code path).

The native Frost and Resources exporters currently require an additional explicit switch (`-Dwp.native.export.frost=true` or `-Dwp.native.export.resources=true`, respectively) alongside `-Dwp.native.export=true`. Their measured export paths remain slower than Java, so the general export switch keeps them on Java while enabling the other native export operations.

With `-Dwp.native.gen=true`, non-dithered terrain painting can filter and paint compact tile planes in a single native transaction. The automatic path currently selects cached built-in brushes with slope filters and bounding-box areas of at least 32,768 cells; brush rectangles are bounded to 256 by 256 cells. `-Dwelt.native.filteredTerrain=false` disables it, while `true` also selects smaller supported footprints and other built-in filter combinations for comparison. Custom filters, custom tile/dimension behavior, dithering, removal and missing native symbols keep the Java path. The direct buffer is reused per worker and capped at 4 MiB; the measured speed gain currently comes with increased allocations and process memory.

Filtered nibble-layer painting and removal can use the same worker buffer with `-Dwelt.native.filteredLayers=true` alongside `-Dwp.native.gen=true`. This path remains explicit because complete-operation measurements show higher memory use. It preserves the original distinction between rounded one-tile removal and truncated multi-tile removal, and replays unsupported unclamped values through Java. Terrain and numeric layers share the versioned WFPT protocol and one native entry point; the former terrain entry points remain compatible.

The same explicit flag also enables non-dithered filtered bit-layer painting and removal, for both block bits and bits shared by a chunk. Predicates reading the output layer use the same packed plane as the writes. Removing an absent bit layer preserves its absent storage and notification behavior; dithering retains the Java random stream. WFPT v3 declares the bit output type without adding a new JNI entry point.

Filtered discrete nibble/byte painting (including annotations and numbered biomes) also uses this explicit flag and shared transaction. WFPT v4 writes constant values independently of the terrain palette, preserving biome values through 255, adjacent annotation nibbles and the removal value captured by the paint constructor. Default writes to absent storage do not create a layer; invalid targets and dithering retain Java behavior.

Complete tile rendering can be selected with `-Dwp.native.render=true -Dwelt.native.viewport=true`. One WVR transaction per tile composes constant surface material colours, compact transparent/pattern/Frost/ReadOnly overlays, indexed biomes/annotations, contours and both terrain/fluid lighting passes. Version 3 adds custom PaintRenderer snapshots and global pattern origins; versions 1 and 2 remain accepted by Rust. Version 2 introduced sparse live biome pattern tables and annotation palettes. Biome 0, automatic value 255, absent patterns, nonzero alpha half mixing and current custom pattern pixels preserve Java behavior. The renderer reuses a bounded direct buffer and prepares only terrain palettes encountered in the view. Exact pixel parity and complete viewport timing are covered by `ViewportRenderParityTest` and `TileViewportBenchmark compare-fused`. This path is explicit: Java allocations increase and process memory measurements do not establish savings. Custom terrain/material calculations, unsupported renderers, biome patterns smaller than 16 by 16, custom providers/schemes, zoom outside -7 through 0, hidden terrain and ceiling/tunnel intersections retain the existing Java path.

`TileViewportBenchmark` also accepts `-Dwelt.benchmark.viewportIndexed=true` to include numbered biomes, automatic biome value 255 and annotations in its complete viewport fixture. Use the `java` mode for the baseline and `compare-fused` for warmed alternating complete redraws with exact pixel comparison. Native benchmark modes require every tile redraw to execute through Rust, preventing partial Java fallback from being reported as a full native result.

For the Rust toolchain setup, exact build commands and details, see `docs/welt/` (start with `docs/welt/README.md` and `docs/welt/CHARTE-ORCHESTRATION.md`).

Height-map editor previews can use `-Dwp.native.gen=true -Dwelt.native.heightMapPreview=true`. The provider reuses the generation program compiler and evaluates a whole 128 by 128 tile in one Rust call, including sampled grids when zooming out. Grey conversion and Graphics2D remain in Java, preserving TYPE_BYTE_GRAY colour-space conversion and clipping. Buffers belong to each rendering worker, and the program is prepared from current map settings each time. Unsupported map types/programs and coordinates outside the exact float/integer domain retain Java. `HeightMapPreviewParityTest` covers complete image parity and `HeightMapPreviewBenchmark compare` measures alternating full viewport redraws; add `-Dwelt.benchmark.previewZoom=-3` for a zoomed fixture. The path is explicit because process memory increases despite unchanged measured Java allocation per redraw.

Normal-zoom slope previews also evaluate the base-map program and slope together inside Rust, sharing a one-cell halo and returning only final slope values. Zoomed slope previews retain Java unless `-Dwelt.native.slopePreviewZoom=true` explicitly selects the experimental sparse-neighborhood path, which measured slower on the complete preview fixture. Add `-Dwelt.benchmark.previewSlope=true` to the preview benchmark; native benchmark modes force that experimental override so slower Rust results cannot be hidden behind Java fallback. The existing height-map JNI entry point shares its validation/program decoder with the new slope entry point.

Transforming height-map previews evaluate affine coordinates and the complete supported base-map program in the same Rust call. Coordinate arrays remain in reusable Rust worker storage; Java sends the six matrix coefficients and receives final heights. Integer-only translation, float rounding and affine operation order follow the original map. Nonfinite transforms, unsupported base programs and inexact integer translation retain Java. Add `-Dwelt.benchmark.previewTransform=true` to measure complete transformed redraws. Pixel comparisons cover translation, scale, rotation, zoom, live map changes and concurrent workers; Perlin/FastNoiseLite heights also match before raster quantisation. The existing smooth banded cosine kernel has a separately tested numeric tolerance of `2e-15` on the unit-height fixture. The complete transformed fixture measured approximately 1.2 to 1.3 times faster in paired warmed runs, with higher process memory, so it remains behind the explicit preview flag.

Displacement previews evaluate angle, distance, displaced coordinates and the complete supported source program inside one Rust call. The three program boundaries are sent together; intermediate planes stay in reusable Rust worker buffers. Regular control grids use prepared Perlin axes, including sampled grids when zooming out; irregular source coordinates retain the point evaluator. Nonfinite displacements, unsupported programs and combined programs exceeding 64 nodes retain Java. Use `-Dwelt.benchmark.previewDisplacement=true` with mode `compare` for alternating full redraw measurements and exact pixel comparisons. The tested fixture measured approximately 1.14 times faster at normal and reduced zoom, with unchanged measured Java allocation but higher process memory. This path uses the existing explicit height-map preview flag.

Custom colour and texture layer overlays also use the complete viewport transaction. The frame carries the renderer snapshot's RGB channels, float alpha and opacity, preserving premultiplied image decoding, Java float operation order and rounding, negative global coordinates and layer priority. Supported BIT, BIT_PER_CHUNK and NIBBLE paints share the existing packed planes. A paint snapshot is limited to 65536 cells and the complete frame remains bounded at 4 MiB; unsupported renderers or dimensions use Java. Use `-Dwelt.benchmark.viewportCustomPaint=true -Dwelt.benchmark.viewportWarmups=20` with `TileViewportBenchmark compare-fused` to compare full redraws. Warmups are configurable from 5 to 100; the benchmark still requires every tile to execute natively. The fixture showed a gain on complete redraws, but higher Java allocation and direct-buffer reservation, with variable process memory; the viewport path remains explicitly enabled.
Viewport benchmark geometry is configurable with `-Dwelt.benchmark.viewportZoom=-2 -Dwelt.benchmark.viewportSide=8` (zoom -7 through 0, side 1 through 16). The fixture displays every selected tile at its actual zoomed size and uses matching image offsets; defaults retain the original 16-tile 512 by 512 view. Combine with custom paint or indexed flags to profile complete zoomed Java redraws. Native comparison requires every tile to run through Rust, so unsupported fixtures cannot report Java fallback as native work. WVR version 4 supports zoom -1 through -7 using only displayed cells and their immediate physical neighbors. Packed overlay planes are sampled under a single tile lock per plane; chunk masks retain their original coordinates. Heights, fluids, overlays and shading share one reusable buffer and one JNI call per tile. A native failure restores the complete Java snapshot before fallback. Existing WVR versions remain accepted.

The 64-tile custom-paint zoom fixture measured complete redraw gains of approximately 1.5, 2.1 and 4.4 times at zoom -1, -2 and -3 in warmed alternating trials, with exact pixels. Separate-process trials also measured higher allocations and peak working set, so this is a speed improvement for the tested views, not a memory reduction or a whole-application gain.

For the imported-height-map preview baseline, use `-Dwelt.benchmark.previewBitmap=true -Dwelt.benchmark.previewWarmups=20` with `HeightMapPreviewBenchmark java`. This fixture composes a 16-bit bitmap, bicubic interpolation and an affine transform; `-Dwelt.benchmark.previewBitmapRepeat=false` selects extended image edges. Use `compare` for alternating complete redraws with exact pixel comparisons and mandatory native tile counts. Preview warmups are configurable from 5 to 100 and successful native tile counts scale accordingly; existing default fixtures are unchanged.

Affine previews over bicubic bitmap height maps now read live source patches in grouped rows and transform/interpolate them inside one Rust call per tile. The direct frame, patch and row storage are reused per worker; Catmull-Rom and float coordinate semantics reuse the import and affine kernels. Supported finite image samples include unsigned 8/16/32-bit and float/double sources. Integer-only translations, oversized patches (over 262144 cells), incompatible replaced bitmap dimensions, nonfinite samples/transforms and inexact coordinates retain Java. Large zoom footprints may therefore fall back. This path shares the explicit generation/height-map preview flags. Complete tested redraws measured roughly 2.1..2.4 times faster; allocations increased, and process memory improved for repeated images but increased for extended edges. `BitmapPreviewParityTest` checks unquantised height bits; GUI preview tests cover actual pixels and live changes.

Bitmap-based world creation can use `-Dwp.native.gen=true -Dwelt.native.bitmapGeneration=true`. WHIM version 3 shares live bitmap sampling, bicubic/affine evaluation, height quantisation, water, terrain and ordered SimpleTheme layer application inside one existing import transaction per tile. Java applies the final packed planes through the normal tile edit mechanisms; empty tile arrays and duplicate initial heights are not copied. Worker buffers are bounded and reused. Factory subclasses, custom themes/raster callbacks, lava factories, incompatible replaced bitmap extents and unsupported/oversized source windows retain Java. Use `BitmapWorldCreationBenchmark compare` with `-Dwelt.benchmark.creationWarmups=20`; `-Dwelt.benchmark.creationSide=8` selects 64 tiles instead of the default 16 (even values 2..16). Native modes reject any tile fallback. Complete measured creation gains were approximately 1.5..1.9 times across 16/64-tile fixtures, with higher allocation and overlapping process-memory ranges. The flag remains explicit; parallel speed is not established.
Procedural world creation can use `-Dwp.native.gen=true -Dwelt.native.proceduralGeneration=true`. WHIM version 4 embeds a bounded WTGP v1 program compiled from current map settings. Perlin/FastNoiseLite trees, arithmetic/shape programs, affine transforms, slope and displacement use the existing Rust kernels; intermediate planes stay in reusable Rust worker storage. Source evaluation, height quantisation, water and SimpleTheme share one JNI call per tile and the existing grouped tile application. Unsupported nested maps, coordinate domains, custom themes and factories retain Java. A transform directly wrapping a displacement map is also compiled as one complete source: affine coordinates, both displacement controls and final samples stay in the same Rust worker buffers (WTGP mode 5). Translation-only wrappers retain the regular-grid control path. Nested unsupported wrappers retain Java. The immutable program contains at most 64 nodes and is copied before theme preparation can invoke custom filters. The shared stochastic theme stream remains protected; concurrent correctness tests do not establish parallel speed.

Select `-Dwelt.benchmark.creationSource=noise|fnl|affine|slope|displacement|affine-displacement` with `BitmapWorldCreationBenchmark compare` for complete creation measurements. On the tested slope fixtures, 16/64-tile creation improved by approximately 7.9/5.9 times, with exact tile fields and random-stream parity. Other source variants were near parity or slower in the measured series, and Java allocations increased by roughly 7 KiB per tile. This experimental flag remains off by default and these measurements are not export gains or a general memory improvement. `-Dwelt.native.generationProfile=true` enables per-worker preparation/native/application timing; `HeightMapTileFactory.nativeGenerationProfile()` returns cumulative successful-call totals. Keep profiling disabled for headline timing measurements. The transformed-displacement fixture measured about 1.10 times at 16 tiles and 1.01 times at 64 tiles, with higher Java allocation and process memory; this source extension remains experimental, not a demonstrated general speed or memory improvement.
Advanced-theme world creation can use `-Dwp.native.gen=true -Dwelt.native.fancyGeneration=true`; add `-Dwp.native.gen.ninePatch=true` for the standard continent/mountain factory. WHIM version 5 snapshots five bounded source programs (height neighborhood, temperature, humidity, forest and local climate perturbation) and runs them with the complete FancyTheme in one existing JNI transaction per tile. Quantised heights, absolute water, terrain and packed layer planes return through the normal grouped tile edit mechanisms. Neighborhoods include the original five-block border and remain unquantised for slope/shoreline decisions. The standard maximum of continent and displaced mountains preserves operand order in Rust. The existing FancyTheme kernel also now follows Java's steep-slope forest exclusion and lazy shoreline branch. Custom themes/maps, distinct factory/theme height maps, lava factories, disabled batching and unsupported domains retain Java.

Use `FancyWorldCreationBenchmark compare`, `-Dwelt.benchmark.creationWarmups=20`, and `-Dwelt.benchmark.fancySource=stock|noise`; `-Dwelt.benchmark.creationSide=8` selects 64 tiles. The fixture pins the effective seed of the otherwise random local climate perturbation so separate JVMs produce the same world; production behavior is unchanged. The measured 16/64-tile standard factory gains were about 1.8 times, versus about 2.8 times for the noise-only height source. These are creation-chain measurements, excluding fixture construction and image/display setup, not Minecraft export gains. Java allocation increased slightly and there is no demonstrated general memory reduction. The flag stays experimental and off by default. Two-worker tests establish independent-buffer parity, not parallel speed.

## Complete nibble-layer brush lines

With the native generation backend enabled (`-Dwp.native.gen=true`), validated slow-mode lines drawn with ordinary `NibbleLayerPaint` now use the complete WSTP v1 tile transaction by default. `-Dwelt.native.lineStroke=false` restores the previous path. Fast-mode lines keep their existing behavior. The adapter supports stock cached symmetric brushes, bitmap brushes and cached rotated brushes, without a filter. Custom callback brushes, unsupported dimensions/tiles, excessive bounds, invalid strengths and missing JNI libraries retain the existing painter.

Java samples the current brush once per complete line. Rust rasterizes the same centers and applies every overlapping impression to the reused packed layer plane, with one JNI call per existing destination tile. No intermediate line-coordinate or block-value arrays return to Java. Nibble targets reuse the existing exact Java-rounding implementation, including the different rounded/truncated erase rules for single-tile and boundary-crossing impressions. Radius-zero strokes preserve brush-level application and unconditional removal notifications for allocated layers. Grouped tile application retains layer presence, copy-on-write, dirty notifications, undo and redo. Worker buffers are bounded and reusable; frame version and lengths are validated before mutations. A replay after a rejected or unavailable native entry is safe because these supported edits are monotone and idempotent.

`LineStrokeBenchmark compare` measures eight complete lines against Java. `compare-existing` uses the previous native line-centers/individual-impression path as the reference. Use `-Dwelt.benchmark.strokeRadius=3|16` and `-Dwelt.benchmark.strokeWarmups=20`; each series uses nine alternating measured pairs and compares the complete layer output. Standalone `java`, `rust` and `previous` modes permit separate-process peak-memory measurements. Fixture creation and GUI redraw are outside the measured stroke; brush sampling, JNI, grouped application and event release are included. These are editor stroke measurements, not export gains or an application-wide speed ratio.

On the measured radius-16/radius-3 fixtures, complete strokes improved by about 4.37/3.77 times versus Java and 1.35/2.79 times versus the previous native impression-by-impression path. JVM warmup, alternating trials and complete-layer parity were required. Ratios vary across trials. Java heap allocation decreased versus the previous native path but increased slightly versus Java alone; the final radius-16 independent-process series measured roughly 115–120 MiB peak for the new path versus 138–146 MiB for the previous native path. These peaks include the JVM and native memory and do not establish lower retained world memory or an application-wide memory reduction.

Complete terrain and binary-layer brush lines now share WSTP v2 with the existing nibble transaction. With `-Dwp.native.gen=true`, automatic selection batches cached, unfiltered brushes whose footprint is at least 1,089 cells and whose footprint times line centres is at least 500,000. Smaller strokes retain the existing painter: measured radius-three lines were slower through the new buffer. `-Dwelt.native.lineSetStroke=true` forces supported sizes for comparison; `false` disables the extension. Terrain application, block-bit and chunk-bit application/removal use one JNI call per destination tile and worker-local buffers capped at 1 MiB. Terrain removal, callbacks, filters, immediate events, custom dimensions/tiles and invalid inputs retain Java.

Dithered constant paints prepare one compact selection with the original Java random stream, including draws over missing tiles and the original short-circuit threshold. Rust applies it once to each tile. A rejected older native ABI reuses that selection through Java, avoiding random replay. Tile application preserves copy-on-write, undo and layer presence. WSTP v1 remains compatible. `LineSetStrokeParityTest` and `LineSetStrokeFallbackTest` cover these paths; `LineSetStrokeBenchmark compare` and `compare-existing` alternate complete eight-line operations after twenty warmups. Select terrain, bit or chunk-bit with `-Dwelt.benchmark.strokePaint=terrain|bit|chunk-bit`, dithering with `-Dwelt.benchmark.strokeDither=true` and radius with `-Dwelt.benchmark.strokeRadius=16`.

On the measured radius-sixteen fixture, complete lines improved approximately 2.0x for terrain and 2.5x for binary layers over Java, or 1.2–1.4x with dithering. These are brush-line results, not application-wide or export gains. Sampled process peaks were similar for terrain (116–117 MiB native versus 117–120 MiB Java), slightly higher for dithered bits (115–116 versus 113–114 MiB); allocations increased about 5 KiB per eight-line operation. No general memory saving is established. Full GUI Maven packaging remains subject to the existing JIDE dependency limitation; the actual painter and parity fixtures were compiled and run against Core with the release native library.

WSTP v3 extends the same complete-line transaction to discrete nibble and byte paints, including annotations and numbered biomes. It preserves the paint's captured removal target independently of the layer's current default, biome value 255, absent default storage, adjacent nibble values and allocated-layer notifications. Dithering keeps the Java random stream and the same prepared-mask fallback after native rejection. The existing size heuristic, `welt.native.lineSetStroke` override and unsupported-case Java fallback apply without another JNI entry point. The benchmark also accepts `-Dwelt.benchmark.strokePaint=biome` or `annotations`. `DiscreteLineStrokeParityTest` adds mutable custom defaults, absent and allocated layers, both directions and undo/redo to the actual painter checks.

Final alternating complete eight-line measurements for radius-sixteen discrete paints gave about 2.5x for biomes and 2.6x for annotations over Java, about 1.6x with dithering. These are editor stroke gains. Native allocations increased roughly 5 KiB per eight-line operation; sampled process peaks ranged from similar to roughly 8 MiB above Java. No memory saving is claimed.

Region-file opening now reads the complete offset/timestamp tables with a grouped channel read and decodes them in one Rust call per region. `welt.native.regionHeader` defaults to true; false restores the original unit reads for comparison. A reusable direct buffer uses at most 8 KiB per worker. Missing native symbols use grouped Java decoding; `-Dwelt.native.regionHeaderKernel=false` selects that control directly. Truncated input replays the original reader, preserving errors from invalid offsets encountered before EOF. File bytes, sector allocation and timestamps keep the existing MCA/MCR format; the buffer address is borrowed only during JNI.

`MapImportBenchmark compare` measures complete disk-backed imports after warmups with alternating Java/Rust order and full output checking. Use `compare-grouped` for grouped-Java attribution, `-Dwelt.benchmark.importSide=8` for 64 chunks, `-Dwelt.benchmark.importWorkers=1` or 4 for fixed worker counts, and `-Dwelt.benchmark.importReadOnly=MAN_MADE` or another ReadOnlyOption. Optional `-Dwelt.profile.mapImport=true` records NBT decoding, chunk construction, surface recognition, tile writes and biome work. Worker durations are summed and are not multithreaded wall time; decoding allocation totals exclude native/direct memory. The harness lives in Core and has no compile-time logging implementation dependency. This optimises region access used by import; it does not port surface classification or the entire Minecraft importer to Rust.

Final alternating complete-import measurements against the original scalar region reader were approximately 3.2x for 64 chunks, 1.7x for 256 and 1.2x for 1024 with one worker, and 3.9x for 64 chunks with four workers. Grouped Java reading performed similarly to the Rust decoder: the gain comes from grouped file access. These are current-Welt importer fixtures, not general export or application gains. Process-memory peaks overlap or increase; no memory saving is established. Six new Java parity tests and 176 release Rust tests pass, and the Core Maven build succeeds.

Chunk loading and Minecraft import now index complete decompressed NBT trees with one JNI invocation per NBT stream, not per tag or block. `welt.native.chunkNbt` defaults to true; false restores streaming JNBT. `welt.native.chunkNbtKernel=false` isolates whole-stream buffering with Java decoding. Worker-local Java/native buffers are reused; the input is copied once into Rust without retaining or pinning JVM arrays. A versioned preorder directory references unmodified UTF-8, floating-point and array payloads. Java reconstructs the existing JNBT types using grouped primitive-array reads. Limits of 4 MiB, 8192 nodes and depth 128 preserve Java fallback; missing symbols/rejected trees reuse buffered bytes, while capture failures or oversize input replay the original stream reader. Custom materials, sidecar tags and version-specific chunk construction retain their existing providers.

`MapImportBenchmark compare-nbt` alternates complete imports with grouped region headers in both modes; `compare-nbt-grouped` isolates the native tree index from buffered JNBT. Standalone modes are `nbt-java`, `nbt-rust` and `nbt-grouped`. Native modes require a successful NBT index for every fixture chunk and equivalent complete world output. On the tested fixtures, complete import improved about 1.4x for 64 chunks and 1.7x for 256/1024 with one worker, and 1.3x for 256 with four workers. Against already-buffered Java NBT the additional gain was about 12%. These gains are relative to the preceding Welt import path, not untouched upstream or export, and must not be multiplied with separately measured milestones. Warmed one-worker allocated bytes decreased approximately 1.9%; process-memory peaks overlap or increase, so no general RAM saving is claimed. Eleven Java parity tests, 180 release Rust tests, Clippy and the Core Maven build pass. Chunk construction, surface classification and compression still run in Java.

The grouped height/theme brush frame now supports themed flatten, raise-only flatten and lower-only flatten. WHTB v2 extends the existing layout; height raise/lower keep v1 compatibility. Older libraries reject the extension before editing or advancing theme RNG, preserving frontend fallback. Height quantisation, unchanged full-flatten theme application, conditional comparisons, layer order and global random draws remain exact. The actual Flatten frontend uses one native call across all intersecting tiles before applying ordered planes through normal edit/undo/event mechanisms. Existing filter/factory/theme fallback and the minimum 16384-cell footprint remain; smaller brushes keep their previous path.

`ThemedFlattenBrushBenchmark compare` and `compare-existing` measure complete eight-stroke operations with full plane/RNG checks, alternating order and twenty warmups. Select radius with `-Dwelt.benchmark.flattenRadius=64` or 127. Measured gains were about 1.6–1.8x over scalar Java and 1.5–1.7x over the predecessor's height-buffer/native-kernel/Java-theme path. These are editor brush results. Allocations increased about 70 KiB per eight strokes; process peaks overlap at radius 64 and were lower for native at radius 127 on the fixture, without a general application-memory claim. Thirteen Java parity tests, 181 release Rust tests, Clippy and the Core Maven build pass. The added headless GUI pipeline test remains unexecuted because clean GUI compilation lacks existing JIDE/dynmap dependencies; full GUI packaging is not confirmed. `HeightBrushAccess.completedThemedCalls()` counts successful grouped native transactions.

The same grouped brush transaction now supports smoothing with SimpleTheme (WHTB v3, mode 5). Java copies only the five-cell external border; interior heights already reside in the shared packed tile planes. Rust captures an immutable neighbourhood in reusable worker storage, sums samples in the original X/Y float order, quantises heights and applies terrain/layers with the original global theme random stream. One JNI invocation covers the entire supported stroke, followed by normal ordered tile application. Filters, custom factories/themes/tiles, unsupported coordinates and small footprints retain the existing path. The existing GUI radius limit (122) is unchanged; old native libraries reject v3 before mutation and preserve frontend fallback.

Use `ThemedSmoothBrushBenchmark compare` or `compare-existing` with `-Dwelt.benchmark.smoothThemeRadius=64|122`, twenty warmups and nine alternating trials. Each measured operation includes eight strokes, force preparation, buffer work, smoothing, theme application and events, with full plane/random-state checking. Measured median paired gains were about 1.2x/1.4x over scalar Java and 1.3x/1.4x over the predecessor's native-height/Java-theme path. Trial ratios varied, including individual slowdowns; these are fixture-specific editor results, not export or application-wide gains. Warmed Java allocation increased about 70 KiB per eight strokes. No general memory improvement is claimed. Seventeen Java parity tests and 183 release Rust tests pass; Core builds successfully. Clippy library checks pass with existing-code allowances; all-target checks still flag older test code. The actual GUI pipeline parity test is provided but remains unexecuted under the existing JIDE/dynmap dependency limitation.

Filtered unthemed height and flatten brushes now share the existing filter/packed-paint transaction (WFPT v5). A 192-byte header adds height mode, adjustment/target, clamps, minimum height and storage kind. Each tile appends X-major raw-height output and a mutation mask. Rust traverses global X/Y order, evaluates filters against live compact planes, quantises each write and refreshes all intersecting height halos before the next filter decision. This preserves evolving slope decisions across neighboring tiles. One JNI invocation covers the complete supported stroke; Java applies masked heights through the standard edit/undo/event path. ## Actual GUI brush pipeline tests

The `welt-brush-tests` Maven profile runs the actual frontend pipeline parity tests with Core's freshly compiled test fixtures on the GUI test classpath, native generation enabled and headless AWT. This tests the production Height, Flatten and Smooth methods rather than substitutes for the GUI operation classes. From the repository root, run:


## Interleaved height and theme preparation

`-Dwp.native.gen=true -Dwelt.native.interleavedTheme=true` opts into WHTB v4. The ordinary bulk path remains the default. The v4 transaction applies each quantised height and its exact SimpleTheme immediately, retaining global X/Y order and Java random draws. Prepared local Perlin axes are reused across cells. No extra JNI call or Java per-cell application is introduced. Unsupported themes and older native libraries retain the existing fallback.

This is the foundation for a fused filtered height/theme operation; the complete filtered path is available separately as an experimental WHTB v5 transaction. The shared automatic-biome classifier is used by both biome baking and existing native filters. WHTB v4 releases the legacy height, terrain and selection work arrays, including inactive cached tiles: 96 KiB per cached tile, up to 864 KiB for nine tiles. The immutable smooth neighborhood is still required. This describes internal work storage, not an application-wide memory saving.

`ThemedHeightBrushBenchmark compare 127` now warms both paths twenty times, alternates nine measured pairs and compares all tile planes and the next theme random value. Eight full strokes include strength preparation, snapshots, JNI, grouped edits and event release; fixture creation and GUI redraw are excluded. Standalone `java` and `rust` modes support process-memory measurements. Initial series measured roughly 2x versus scalar Java but did not establish a gain over the preceding native bulk path; timing and process peaks overlap across runs. Java heap allocation is higher in the native path. Keep v4 experimental while the complete filtered pipeline is built and measured.

## Grouped filtered height and theme transactions

`-Dwp.native.gen=true -Dwelt.native.filteredThemedHeight=true` enables WHTB v5 in the Height, Flatten and Smooth GUI operations. The shared packed planes hold heights, water, terrain, theme layers and filter dependencies. A compiled filter reads these planes after preceding cells have been changed, then quantised height and SimpleTheme run in the original X/Y order. Slope uses a one-cell border; smoothing additionally uses its immutable five-cell neighborhood. Java imports each modified tile through the grouped edit and undo mechanisms. Each supported stroke makes one JNI call across all participating tiles.

The v5 header is 256 bytes. It declares the filter program, shared terrain/biome palette, border, dynamic strength and helper plane indices. Rust validates the complete metadata and theme palette before changing planes or advancing the random stream. Versions 1 through 4 remain supported. Small strokes, unsupported filters/themes/tile classes and unavailable native libraries use the existing Java fallback. The flag is off by default.

`FilteredThemedHeightBrushBenchmark compare` measures eight complete strokes per sample, including filter compilation, strength preparation, buffer copies, JNI, grouped application and event release. The default series warms both paths twenty times and alternates nine measured pairs. It compares all planes and the next theme random value outside timing. Standalone `java` and `rust` modes allow independent process-memory sampling. Fixture creation and screen repaint are outside the timed operation. Configure radius/mode with `welt.benchmark.filteredThemeRadius` and `welt.benchmark.filteredThemeMode`.

## Grouped mountain shaping with theme

`-Dwp.native.gen=true -Dwelt.native.themedMountain=true` opts into the complete Raise Mountain transaction for supported brush radii 64 through 127. WHTB v6 keeps a 128-byte header and adds modes 6/7 (raise/lower mountain), peak factor at byte 88 and noise scale at byte 92. The kernel uses the existing seed-67 Perlin semantics and Java float expression order. Prepared noise coordinates, packed tile storage and theme workspaces are reused by the worker. Shaping, quantisation and SimpleTheme mutations run together in global X/Y order, with one JNI call and grouped tile application. Unsupported themes, metadata, dimensions and older native libraries retain the previous path. The flag is off by default.

`ThemedMountainBrushBenchmark compare 127` alternates nine measured pairs after twenty warmups per path. Eight strokes include brush strength preparation, snapshots, noise/shaping, theme, JNI, grouped edits and event release; fixtures, plane/RNG comparisons and screen repaint are outside timing. `java` and `rust` modes support independent process-memory measurements. `-Dwelt.benchmark.mountainLegacy=true` compares the earlier native-height calculation followed by per-cell Java height/theme application; its arrays are reused and its output is checked against the same Java reference. JFR event `welt.ThemedMountainStroke` bounds the timed operations for profiling. Functional tests compare short/tall height storage, special forces, negative coordinates, holes, random draws, undo/redo and actual GUI dispatch. Runtime gains are specific to this operation; allocations and process peaks do not establish a general memory improvement.
